# Deriv R_100 Digit-Over-2 Probability Bot

A probability-calibrated, multi-model signal engine for `DIGITOVER`
contracts (barrier 2) on Deriv's R_100 synthetic index, built against
the master spec in your original prompt, with one deliberate,
explicitly-labeled deviation: **the full walk-forward validation
engine was replaced with a single chronological train/test split**
(`validation/quick_validation.py`) so this could be built in one
session instead of over weeks. Read "What was cut and why" below
before trusting any numbers this produces.

## Read this before anything else

**R_100's last digit is generated by a random number generator that
Deriv designs and audits specifically to be memoryless and uniform.**
That is the entire point of a "volatility index" product - it exists
to *not* have exploitable structure. This system is built to the full
rigor requested (multi-model, calibration, agreement checks, EV
gating, risk controls) and it works correctly end-to-end. But built
correctly on data with no real edge, the honest, expected output is:

- calibrated probabilities converge to ≈0.70 (the true uniform rate),
- the bot outputs `NO_TRADE` on almost every tick, because 0.70 never
  clears the required threshold (0.76+) with any real margin,
- on the rare occasion a threshold IS cleared, it's very likely
  sampling noise, not a real edge - the calibration report will show
  this director if you feed it enough live data (predicted-vs-actual
  drift in the bucket table).

Run `main.py` on real R_100 history and you should expect to see
exactly this. **That NO_TRADE-heavy output is the system succeeding,
not failing.** If you instead see it trading constantly at high
confidence on real data, be suspicious of a bug (most likely: the
calibrator being fit on too little data, or a model quietly leaking
information) before you trust it.

Separately, Deriv's real payout on this contract is below fair odds
(house edge), so even a genuinely-uniform 70% win rate loses money
over time on stake-weighted average - see the `always_trade_over2`
baseline in every report for the concrete number.

None of this is a reason not to have built it properly - it's the
reason the system is built to *refuse to trade* by default rather
than to find profit that isn't there.

## What was cut and why (per your "no time" instruction)

| Spec section | Full spec asks for | What's here instead |
|---|---|---|
| §21 Walk-forward | Rolling/expanding re-fit across many periods | **One train/test split** (`quick_validation.py`). Calibration is fit once on the train slice and frozen for the entire test slice. |
| §14 Calibration | Isotonic regression / Platt scaling | A bucketed reliability mapping (`models/calibration.py`) with a minimum-sample trust gate per bucket. Conceptually the same idea, much simpler math. |
| §12 Regime detection | Learned regime classifier | Threshold-based classifier on dispersion + entropy (`trading/regime.py`) - transparent but not learned/validated itself. |
| §26 Online monitoring / drift detection | Continuous live recalibration | Not built. The live loop (`main.py: run_live`) fits calibration once from the first ~3×`min_history_size` ticks and never refits. For a real deployment you'd want to periodically re-run `quick_validation` on recent data and swap in a fresh calibrator. |
| §31/§32 Full test coverage | Tests for every listed behavior | 22 unit tests covering the pieces most likely to hide a real bug (digit extraction, window math, calibration math, EV math, martingale progression + no-auto-continue, risk halts, config safety guard). Not exhaustive. |

Everything else in the spec (multi-window empirical model, Bayesian
Beta-Binomial, Markov order 1/2/3 cascade, run-length, W/L-run pattern
model, raw digit-sequence pattern model (2 and 3 digit lookback),
chi-square/z-score statistical significance testing, entropy, adaptive
ensemble weighting by rolling Brier score, EV gating on real payout,
martingale with independent re-evaluation per level, hard risk limits,
explicit state machine, explainable per-tick logging, safe default
mode) is implemented and shared identically between the simulator and
the live loop - see `validation/historical_simulator.py` and
`main.py:run_live`, which both call the same `SignalEngine`.

### On the significance model specifically

`models/significance_model.py` runs a chi-square goodness-of-fit test
(digit counts vs. uniform) and a z-test (P(over2) vs. the 0.70
baseline) and only contributes an ensemble vote when one of them is
significant at alpha=0.05 - otherwise it abstains. This is a genuine
statistical upgrade over "does the raw probability look high": models
agreeing that a window looks unusual now means something falsifiable.

It is not, on its own, proof of a tradable edge. On truly random
digits this model will still flag ~5% of windows purely by chance
(that's what alpha=0.05 means) - that's the test working correctly,
not a bug. Whether flagged windows have historically predicted
anything is exactly what the calibration bucket table in the report
checks: if 70-80%-bucket trades (which is where a significance-driven
signal would land) show an actual win rate meaningfully above 70%,
out of sample, that's real. If it tracks the bucket center, it isn't -
no matter how many models "agreed" going in.

## Architecture

```
config.py                  - all tunables, env-driven, safety guard on live modes
features/
  digit_extractor.py        - quote -> last digit at correct pip precision
  rolling_windows.py         - O(1)-update multi-scale windows (10..1000 ticks)
  digit_statistics.py        - frequency, z-score, Wilson CI on P(over2)
  transition_features.py     - 1st/2nd order Markov, W/L grouped
  run_features.py            - run-length tracking + next-outcome stats
  entropy_features.py        - Shannon entropy, normalized
  feature_engine.py          - orchestrates all of the above per tick
models/
  base.py                    - ModelOutput contract
  empirical_model.py, bayesian_model.py, markov_model.py,
  run_length_model.py, pattern_model.py, significance_model.py,
  digit_sequence_model.py
  ensemble.py                - adaptive weighting by rolling Brier score, agreement/dispersion
  calibration.py              - bucketed calibration, see limitations above
trading/
  expected_value.py           - EV from ACTUAL payout, never assumed fair odds
  martingale.py                - stake/level tracking ONLY, no auto-continue
  risk_manager.py              - hard daily loss / drawdown / consecutive-loss halts
  regime.py                    - NORMAL / MODEL_CONFLICT / UNSTABLE gate
  signal_engine.py              - the single decision point, every gate must pass
  trade_state.py                - explicit state enum
validation/
  metrics.py                    - win rate, drawdown, profit factor, Brier, log loss, calibration buckets
  historical_simulator.py       - sequential no-lookahead replay
  quick_validation.py           - the train/test split described above
deriv/
  client.py                     - OTP-bootstrap WS client, corrected schema
data/storage.py                 - sqlite persistence for ticks/signals/trades
main.py                         - CLI entry point, both simulation and live modes
tests/test_core.py               - 22 unit tests, run with `python -m unittest tests.test_core -v`
```

## Running it

```bash
pip install -r requirements.txt

# Historical simulation (default & safe - no network, no money)
python main.py --data your_ticks.csv --decimals 2

# If your CSV already has a 'digit' column, --decimals is ignored.
```

CSV format: either a `digit` column (0-9), or a `quote` column (the
script will extract the digit at the given `--decimals` precision the
same way the live code does).

A synthetic sample (`sample_ticks.csv`, true-random digits, NOT real
R_100 data) is included purely to prove the pipeline runs - do not
draw any conclusion about real market behavior from it. **Feed it real
R_100 tick history before trusting any output.**

Tests:
```bash
python -m unittest tests.test_core -v
```

## Going to DERIV_DEMO or LIVE

```bash
MODE=DERIV_DEMO CONFIRM_LIVE=true DERIV_APP_ID=... DERIV_TOKEN=... python main.py
```

`Config.validate()` refuses to start in `DERIV_DEMO` or `LIVE` without
`CONFIRM_LIVE=true` explicitly set - this is intentional friction, not
a bug. The live loop:

1. Connects and subscribes to `SYMBOL` ticks.
2. Spends the first ~3×`MIN_HISTORY_SIZE` ticks purely collecting data
   to fit the calibrator - **it will not place a single trade before
   this finishes**, printed to console when it does.
3. After that, runs the exact same `SignalEngine.evaluate()` used in
   the simulator, on live proposals with real payout figures.
4. In `DERIV_DEMO` mode it evaluates and logs everything but does not
   call `client.buy()` in this reference build - wire that in once
   you've watched a run and are satisfied the signals look sane. In
   `LIVE` mode it does call `buy()`.

This live path has been written to the same schema and object model as
the simulator and passes basic smoke tests, but **has not been run
against a real Deriv connection** as part of this build. Watch the
first session closely on `DERIV_DEMO` before ever setting `MODE=LIVE`.

## Account selection

`DerivClient` auto-selects an account matching the current mode:
`DERIV_DEMO` requires a virtual/demo account, `LIVE` requires a
real-money account. It refuses to silently fall back to the wrong
type - if no matching account is found, or more than one matches
without a token telling it which, it either raises an error or logs
which one it picked and why. If you have multiple accounts of the
same type (e.g. two real-money currencies), set `DERIV_ACCOUNT_ID` in
`.env` to pick explicitly rather than relying on "first match."

On `DERIV_DEMO`/`LIVE` startup it also fetches one diagnostic proposal
and prints the **actual breakeven probability** implied by Deriv's
real payout for your configured stake - this is the number any
threshold decision should be based on, not the textbook 70%. If your
models cap out below that number, that's the honest finding, and no
amount of threshold-lowering changes it: the EV gate is a hard
arithmetic check, not a matter of preference.

## Railway deployment

`Procfile`, `railway.json`, and `nixpacks.toml` are included for a
worker-process deployment (this is a long-running process, not a web
service - there's no HTTP port to bind). Set your env vars
(`DERIV_APP_ID`, `DERIV_TOKEN`, `MODE`, `CONFIRM_LIVE`, etc.) in
Railway's dashboard rather than committing `.env`. The process handles
`SIGTERM` (what Railway sends on redeploy) by finishing the current
tick, closing the websocket, and closing the sqlite connection
cleanly rather than being killed mid-write.

**Do not set `MODE=LIVE` and `CONFIRM_LIVE=true` in Railway's env vars
until you've watched a `DERIV_DEMO` deployment run for a real session**
- a background worker with no one watching it is exactly the situation
where a bug in a market-order path is most costly.

## Martingale risk, explicitly

Default config: base stake 0.35, multiplier 3.1, 3 steps. Full-cycle
exposure if every level loses: **≈15.2** (see
`MartingaleState.total_cycle_exposure()`). Under a true 70% win
probability the chance of 4 straight losses is `0.3^4 ≈ 0.81%` *per
cycle* - not negligible over any real volume of trading. The bot
re-evaluates every martingale level against a fresh, independently-
higher confidence threshold (never auto-continues), but that reduces
frequency of deep martingale runs, it does not make them impossible.
